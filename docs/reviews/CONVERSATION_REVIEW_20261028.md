# 对话复盘

## 复盘范围

本次复盘覆盖近期围绕本仓的任务：V1.4 目标与阶段交付、飞控参数和工具路由、核心执行策略、平台执行器与航线规则、会话/任务状态恢复、控制权与悬停门禁，以及 2026-10-28 的文档整理任务。线程摘要显示这些任务反复围绕同一条主线推进，而不是彼此独立的产品需求。

## 实际形成的工作模式

1. 先从设计规范、现有源码和评测报告找缺口。
2. 把危险动作、权限、状态版本、控制权和真实平台能力放到确定性代码中，默认模拟器或 unavailable/fail-closed。
3. 按阶段提交小改动，跑离线测试、契约 mock 和隔离实例，并把结果写入 acceptance/evidence。
4. 遇到真实平台缺少快照、租约、回执或授权时停止向设备推进，保留代码和契约层进展。

这个模式的优点是安全边界清楚、负面证据保留完整、能够持续交付；它也解释了为什么仓库的代码和离线证据增长很快，而真实闭环没有同步增长。

## 已验证的有效做法

- 用只读探针先确认代码、配置、分支、端口和外部状态，再决定是否修改。
- 把“模拟器完成”“请求已受理”“回执未知”“设备完成”分开记录。
- 对缺失的 `route_status`、控制权、算法来源和测绘事务采取 fail-closed。
- 真实平台前先做 mock/fixture/隔离端口验证，且保留停止和清理记录。
- 在 [convergence gate 作废记录](../evidence/convergence_gate_20261031.md) 中承认“单 Agent 自产自验”和“前端走查未执行”，这为后续独立复核留下了明确反例。

## 暴露出的流程问题

- **状态入口重复**：`README.md`、`CONTINUE.md`、V1.4 主验收、阶段验收和 evidence 同时描述“当前完成度”，时间点和测试分母容易漂移。
- **证据没有统一元数据**：很多文件缺少 `status`、`code_sha`、`evidence_level`、`unknowns` 和 `next_action`，读者只能从正文猜测有效期。
- **历史结论容易被误读**：V14 阶段文档仍引用旧基线和旧分母；作废报告虽有标题提示，但没有统一索引和替代关系。
- **对话范围会膨胀**：从一个缺口扩展到跨仓、前端、Java、平台和实机前置条件，新增工作会稀释当前验收目标。
- **“通过”语义不够窄**：单测、mock、HTTP 200 和 `submitted` 偶尔被读成更高层级的业务完成，需要每次显式写证据层级。
- **工作树卫生风险**：评测目录、压缩快照和 memory 目录未跟踪，容易把临时产物误当作当前交付物。

## 后续固定交接模板

每次任务结束只保留下面八项，正文可以很短：

1. 用户目标与本轮验收口径；
2. 已授权范围和明确禁区；
3. 基线（仓库、分支、HEAD、脏改动、外部依赖）；
4. 事实探针与负面证据；
5. 改动文件和行为变化；
6. 实际验证命令、输出和证据等级；
7. 未验证、阻塞、风险和副作用；
8. 下一步、负责人、前置条件和回滚方式。

对话摘要只能说明“做过什么”，不能替代这八项中的验证证据。`.workbuddy-ai/memory/` 只能作为内部线索，产品文档必须回指源码、测试、fixture 或平台回执。
